# Подготовка к техническому собеседованию

Ниже ответы привязаны к фактической реализации этого репозитория. Там, где возможности нет, указан возможный следующий шаг, а не результат, которого проект достиг.

## RAG, поиск и оценка

### 1. Что такое RAG?

Retrieval-Augmented Generation — подход, в котором система сначала извлекает релевантные документы, затем передаёт найденные фрагменты модели как контекст. Это помогает ссылаться на актуальную базу знаний и ограничивать ответ имеющимися материалами, но не гарантирует правильность автоматически.

### 2. Как устроен RAG в проекте?

PDF/TXT/Markdown преобразуются в текст, фильтруются от нескольких очевидных строк prompt injection, делятся на фрагменты, векторизуются и сохраняются в SQLite. При вопросе вычисляется cosine similarity, затем найденные фрагменты передаются в генератор; API возвращает документ и идентификатор chunk.

### 3. Что такое embeddings?

Это числовое представление текста, чтобы близость смыслов приближённо измерялась геометрической близостью векторов. В прототипе по умолчанию используются детерминированные hash word/character n-gram vectors и маленький RU/KK словарь понятий; полноценная мультиязычная модель Sentence Transformers подключается опционально.

### 4. Почему выбрана векторная база SQLite?

Для небольшого локального демо SQLite хранит документы, профили, chunks и JSON-векторы без отдельного сервиса. Cosine similarity считается в Python линейным проходом, поэтому это переносимо и прозрачно, но не подходит для большого корпуса; при росте можно мигрировать на Qdrant или другой ANN/vector store.

### 5. Насколько текущие embeddings семантические?

Hash/ngram vectors полезны для локального retrieval похожих словоформ и небольшого списка RU/KK соответствий, но уступают pretrained multilingual embeddings в парафразах и переводе. Это честный offline fallback. В README описано подключение `intfloat/multilingual-e5-small`, после чего нужно переиндексировать документы.

### 6. Как выбраны размер и overlap фрагментов?

Текущие значения — максимум 900 символов и перекрытие 120. Это стартовая настройка для коротких синтетических памяток; её следует подбирать на реальном разрешённом корпусе по retrieval recall, качеству цитат и длине контекста модели.

### 7. Как выбираются найденные источники?

Для вопроса строится вектор, документы ранжируются cosine similarity, применяется порог `MIN_RETRIEVAL_SCORE` и берётся `TOP_K` (по умолчанию 4). Это объяснимый baseline, но для модели embeddings и разных тематик порог надо калибровать отдельно.

### 8. Как формируется ссылка на источник?

Ответ включает название документа, `document_id` и ссылку вида `document_id#chunk-N`, а также ограниченный текстовый snippet и score. Это локальные идентификаторы проекта, не публичные web citations.

### 9. Что происходит, если данных нет?

Если лучший retrieval score ниже порога, модель не вызывается: API возвращает пустой список источников и фразу о недостатке информации на определённом языке. В наборе оценки есть вопросы, у которых нет ожидаемого ответа.

### 10. Как измеряется groundedness?

Автоматический отчёт использует простой proxy: extractive ответ должен содержать текст из процитированного фрагмента. Это доказывает только связь текста ответа с найденным фрагментом, но не проверяет полноту, истинность или понятность. Нужна ручная оценка.

### 11. Как предотвращается prompt injection из документов?

Индексация удаляет строки с набором известных формулировок-инъекций, а системный prompt отдельно помечает retrieved context недоверенным и запрещает исполнять инструкции из него. Оба слоя эвристические, могут пропустить атаку и не заменяют защитные тесты или изоляцию инструментов.

### 12. Почему нельзя полностью доверять источнику, даже если он найден?

Retrieval отвечает на вопрос «похоже ли это на запрос», а не «истинен ли документ». Нужно проверять автора, дату, лицензии и актуальность; для родительских рекомендаций — отдельно получать утверждение квалифицированного специалиста.

## Модели, LoRA и inference

### 13. Что такое LoRA?

Low-Rank Adaptation замораживает базовые веса и добавляет небольшие обучаемые матрицы к выбранным линейным слоям. Так можно хранить и обучать компактный adapter вместо полного checkpoint.

### 14. Что такое QLoRA?

QLoRA загружает замороженную базовую модель в низкой точности, обычно 4-bit NF4, и обучает LoRA-параметры. В скрипте есть 4-bit `BitsAndBytesConfig` и подготовка модели для k-bit training; запуск требует совместимой CUDA GPU и bitsandbytes.

### 15. Чем fine-tuning отличается от RAG?

RAG добавляет внешние факты при каждом запросе, их можно обновлять без переобучения модели. Fine-tuning меняет поведение и распределение ответов модели; он лучше подходит для формата/стиля, но не является надёжной базой актуальных фактов. Текущий прототип имеет оба воспроизводимых контура, но LoRA не обучался.

### 16. Что такое квантизация?

Это представление весов меньшим числом бит, чтобы уменьшить память и иногда ускорить inference ценой возможной потери точности. В API квантизацию делает выбранный runtime модели; QLoRA pipeline задаёт 4-bit NF4 во время загрузки.

### 17. Зачем здесь PyTorch?

PyTorch используется только отдельным модулем обучения и загрузки adapter через Transformers/PEFT. RAG API по умолчанию не требует PyTorch и запускается на стандартном Python.

### 18. Как используется Hugging Face?

Скрипт получает tokenizer и causal LM из Transformers, датасет JSONL через Datasets, настраивает LoRA через PEFT и запускает `Trainer`. Имена моделей не скачиваются автоматически, пока пользователь не запустит training/inference скрипт.

### 19. Как запускаются Qwen или Llama?

Для интерактивной генерации API может обращаться к Ollama по HTTP, пример настройки — квантованный тег `qwen2.5:3b-instruct-q4_K_M`. Через Transformers можно выбрать модель из доступных репозиториев Hugging Face, если соблюдены её лицензия и условия доступа. Llama отдельным образом в текущем API не проверялась.

### 20. Что контролирует конфигурация генерации?

Провайдер, URL, имя модели, температура, max tokens и таймаут задаются переменными окружения. При ошибке Ollama/API запрос не раскрывает внутренний ответ провайдера и переключается на extractive fallback.

### 21. Обучалась ли модель и какие метрики получены?

Да. Я обучил Qwen2.5-0.5B-Instruct через QLoRA 4-bit NF4 на RTX 3050: 16 train примеров, 4 validation, 1 эпоха и 2 шага. Validation loss — 2.3581. На 8 синтетических holdout примерах exact-term recall proxy остался 0.0833, abstention accuracy — 0.75. Это честный отрицательный результат короткого эксперимента: казахские ответы и медицинский отказ недостаточно качественные. Адаптер, логи и ответы сохранены в `finetuning/results/qwen-qlora/`; он не готов для пользователей.

### 22. Как сравнить базовую и дообученную модель?

`finetuning/evaluate_adapter.py` запускает обе модели на выделенном test split, сохраняет ответы и считает exact expected-term recall и маркеры отказа. `compare_base_adapter.py` остаётся удобным для произвольных промптов. Ни один автоматический proxy не заменяет слепую оценку человеком.

## Мультиязычность и персонализация

### 23. Как сейчас определяется язык?

Если найдена специфичная казахская буква, выбирается `kk`; короткий латинский или очень короткий текст может использовать язык профиля; иначе выбирается `ru`. Это лёгкая эвристика и слабое место для смешанных фраз без уникальных казахских букв.

### 24. Как улучшить казахский язык?

Нужны лицензированные экспертно проверенные казахские материалы, полноценная multilingual language detector и embedding модель, затем отдельные тестовые примеры на кириллических вариантах и code-switching. Перед демонстрацией ответа должен пройти ручную проверку носителем языка.

### 25. Что происходит со смешанным RU/KZ запросом?

Любая казахская специфичная буква выбирает `kk`; весь смешанный текст при этом подаётся retrieval целиком. Для кода без таких букв срабатывает русский fallback, поэтому улучшение detector и тестирование mixed запросов — следующий шаг.

### 26. Как используется профиль ребёнка?

Хранятся только возраст в месяцах, предпочитаемый язык, интересы, доступные материалы и пожелания родителей. Поля передаются генератору и слегка влияют на score retrieval. Имя и дата рождения не требуются; система не делает выводов о здоровье или развитии.

### 27. Как исключаются необоснованные выводы о здоровье?

System prompt запрещает диагностику и выводы о здоровье/развитии, профилю приписывается роль предпочтений, а при нехватке источников ответ воздерживается. Это полезный слой, но не сертификация медицинской безопасности; нужны red-team кейсы, экспертный контроль и process escalation.

## API, безопасность и эксплуатация

### 28. Как масштабировать FastAPI?

Stateless API можно запускать несколькими workers за reverse proxy и отделить тяжёлый inference в model-serving сервис. Но SQLite и in-process Ollama calls имеют ограничения; перед масштабированием нужны внешняя БД, очередь длительной индексации, rate limiting и измерения нагрузки.

### 29. Как устроена валидация API?

Pydantic ограничивает возраст 0–35 месяцев, длину полей, язык, списки и неизвестные поля. FastAPI формирует OpenAPI и стандартные 4xx ошибки.

### 30. Как ограничивается загрузка файлов?

Allowlist из PDF, TXT, Markdown, ограничение размера (default 5 MiB), числа страниц PDF (50), проверка UTF-8 и минимальной длины текста. Имя нормализуется до basename, оригинальный файл не сохраняется. Reverse proxy тоже должен ограничить размер HTTP body до передачи приложению.

### 31. Как разделены данные пользователей?

API secret сопоставляется с principal. Обычный principal не может задать чужой `X-Owner-ID`, поэтому профили и файлы фильтруются по владельцу. Доверенный отдельный principal Telegram может задавать owner из Telegram user ID; утечка этого service key даёт более широкие права и требует аккуратного хранения.

### 32. Где хранятся секреты?

Только в переменных окружения или неотслеживаемом `.env`; `.env` внесён в `.gitignore`. В примере только плейсхолдеры. В production нужны secret manager, ротация ключей и разделение dev/staging/prod.

### 33. Какие персональные данные сохраняются?

В профиле — указанные пользователем предпочтения, возраст в месяцах, интересы и материалы; имя не запрашивается. Чаты и вопросы не сохраняются. SQLite-файл на диске не зашифрован, поэтому реальные профили детей в демо использовать нельзя.

### 34. Есть ли аудит и rate limit?

Есть JSON-логи события/провайдера/времени, без текста вопроса и ключей. Rate limiting, распределённое tracing и централизованный мониторинг не реализованы; это production задачи.

### 35. Как развернуть модель на GPU-сервере?

Выбрать модель и разрешённый runtime, проверить драйверы/CUDA/VRAM, запустить model server отдельно от API, ограничить сеть и credentials, настроить health/readiness, таймауты, очередь и мониторинг памяти/latency. В этом проекте проверен только интерфейс интеграции; GPU deployment не выполнялся.

### 36. Как снизить стоимость inference?

Отвечать extractively при достаточном контексте, использовать небольшой подходящий модельный размер, квантизацию, ограничивать top-k/context/max tokens, кэшировать публичные embeddings/частые запросы и измерять cost per supported answer. Кэширование профилей и ответов потребовало бы отдельной проверки приватности.

### 37. Какие health checks есть?

`GET /health` проверяет чтение SQLite и сообщает активные embedding/generation backend. Docker выполняет HTTP-запрос к нему. Проверка сейчас не делает probe к Ollama/API; поэтому `status=ok` не означает, что внешний провайдер доступен.

### 38. Как работает Telegram-интеграция?

Это небольшой long-polling клиент на стандартной библиотеке Python, который проксирует запрос в FastAPI по отдельному API key. Реальная работа требует Telegram token, которого в репозитории нет и который не проверялся. Последние источники и текущий профиль в боте кэшируются в памяти процесса.

## Evaluation, CI/CD и развитие

### 39. Какие метрики RAG рассчитываются?

Source hit для ожидаемого документа, MRR, recall заданных evidence-фраз в retrieved snippet, точность abstention, стабильность повторного retrieval и latency. Это фиксированные proxy для компактного synthetic dataset, а не production benchmark.

### 40. Как сравнивается RAG с обычной LLM?

Детерминированный evaluation включает контекстно-свободный extractive baseline: без retrieved context он воздерживается, поэтому не создаёт grounded citations. Это показывает дополнительное покрытие фактов/источников, но не сравнение языкового качества двух LLM. Для честного A/B нужен одинаковый provider и одинаковые вопросы, с RAG/no-context вариантом, бюджетом токенов и слепой оценкой.

### 41. Почему не использовать LLM judge как единственный критерий?

LLM judge может воспроизводить собственные ошибки, предпочтения к стилю и систематические смещения по языку. Поэтому в проекте есть ожидаемые источники/evidence criteria и ручная rubric; автоматический оценщик допустим только как дополнительный сигнал.

### 42. Что делать при ухудшении качества?

Сначала сегментировать по языку, теме, типу документа и версии модели; проверить, это retrieval, source coverage, prompt или generation. Сравнить с предыдущим фиксированным regression set, изучить промахи, исправить корпус/чанки/threshold отдельно от генерации, затем повторить offline и canary оценку.

### 43. Что делает CI?

GitHub Actions ставит runtime/dev зависимости, компилирует модули, запускает pytest и детерминированный evaluation. После исправления discovery `app` модулей опубликованный workflow прошёл на GitHub Actions run #2; workflow не обучает модель и не запускает CV inference.

### 44. Реализован ли ML CD?

Нет. Есть CI для кода, но нет регистрации артефактов модели, approval gate, canary deploy, rollback или production ML pipeline. Следующий шаг — immutable model/config/version registry и promotion только после измерений и проверки безопасности.

### 45. Есть ли компьютерное зрение или обработка видео?

Да, добавлен отдельный optional endpoint `/vision/analyze`: OpenCV семплирует до 30 кадров короткого ролика, Ultralytics YOLO возвращает классы, confidence, координаты рамок и latency. Второй продукт студии закрыт, поэтому это переносимый video inference пример, а не утверждение о его конкретной задаче. Модель COCO общая, tracking и целевой датасет отсутствуют, CV метрики не измерялись. VTT/SRT/TXT-субтитры отдельно индексируются в RAG; ASR не реализован.

### 46. Какой известный технический риск самый существенный?

Текущий hash/ngram vectorizer может не найти парафраз или далеко переводящий запрос, а prompt-injection фильтр не покрывает все атаки. Поэтому демо показывает архитектурный skeleton; перед продуктовым использованием нужны pretrained multilingual embeddings, экспертные данные, adversarial набор и ручная оценка.

### 47. Что не следует обещать по этому проекту?

Нельзя говорить, что LoRA обучен, что CV модель адаптирована под целевой сценарий, что ответы педагоги одобрили, что казахский прошёл полноценную оценку, что injection исключён или что система production-ready. Подтверждены кодовые пути, локальные тесты и retrieval proxies; fine-tuning и CV качество не измерялись.
